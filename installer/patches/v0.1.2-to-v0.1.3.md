# Patch 0.1.2 → 0.1.3: Checkpoint-Batched Writes

## Preconditions

- Require Package ID `root-engineering-chat-installer` and Package Version `0.1.2` in both Manifests.
- Require one unambiguous Project Binding and readable Global Protocol and Project Instructions.
- If either version differs, stop without mutation.

## Operations

Add or replace the corresponding write-efficiency rules in the Global Protocol and Project Instructions. Preserve unrelated sections and document IDs.

### Root Update Buffer

Maintain a small, in-context, non-persistent candidate list during active work. Each candidate records only the target document ID, semantic key or section, proposed add/modify/supersede operation, authority and verification basis, and one write class:

- `IMMEDIATE`: the next action could become unsafe or materially wrong if the change is deferred.
- `CHECKPOINT`: a verified work-state change that may be combined with related changes for the same document.
- `DISCARD`: transient, unverified, duplicate, or not worth preserving.

Never create a Buffer document in Drive. Do not treat buffered candidates as authoritative before a successful write and verification.

### Flush rules

Flush immediately for critical decision-path changes. Flush checkpoint candidates when the user asks to save, sync, checkpoint, hand off, or close; when a coherent unit of work completes; or when several compatible candidates for one document can become one minimal patch.

At a flush:

1. Re-read the affected scope once unless it was just read and its revision is known current.
2. Re-evaluate authority and discard invalid candidates.
3. Group compatible candidates by target document; never parallelize writes to the same document or dependent structure.
4. Apply one minimal patch per target instead of regenerating a whole document.
5. Prune duplicates, superseded content, and stale pointers only inside the already-read affected scope.
6. Clear candidates only after verification succeeds; retain them after a failed write.

Update the ROOT Map only when topology, routing metadata, or its digest changed. A content-only change inside an existing branch does not by itself justify a ROOT Map write.

### Risk-tiered verification

- Routine content patch: read the changed scope and confirm semantic key, value, boundary, and revision when available.
- Critical state patch: read the complete affected logical section, confirm superseded state is not current, and verify authority, provenance, and revision when available.
- Structural patch: verify destination content, child and parent maps, navigation path, and folder boundary before cleanup or Trash.

## Verification

- No persistent Buffer document exists.
- Compatible checkpoint changes to one document produce one write and one proportional verification read.
- A critical decision-path change still writes immediately.
- Content-only branch updates do not rewrite the ROOT Map.
- Structural cleanup occurs only after destination and navigation checks pass.

Only after all checks pass, set Package Version to `0.1.3` in both Manifests and re-read both values. Keep Schema Version `0.1.0`.

## Failure

On failure, leave both Manifest versions at `0.1.2`, retain unapplied candidates in context when possible, identify the failed scope, and stop.
